## 3. 운영 처리 상태 (고객별 식별정보는 비공개 시스템에만)
`RECEIVED_UNVERIFIED` → `RECEIPT_CONFIRMED` → `CLASSIFIED` → `ASSIGNED` → `INVESTIGATING` → `WAITING_CUSTOMER` 또는 `READY_FOR_REVIEW` → `RESOLVED_BY_HUMAN` → `CLOSED_AFTER_CONFIRMATION`.

- `RECEIVED_UNVERIFIED`: 양식 제출 성공 화면/고객 스크린샷일 뿐 실제 도착 확인 전.
- `RECEIPT_CONFIRMED`: Netlify Forms 관리화면 또는 공식 메일 수신함에서 원본을 실제 확인한 뒤 부여.
- 접수 ID는 비공개 시스템에서 생성하며 GitHub에는 PII를 남기지 않는 익명 장애 유형 및 CI 링크만 기록.
- 고객에게 자동 응답·약속한 일자·처리완료 표시를 내기 전에 확인된 접수와 담당자 상태가 필요.

## 4. 매일 점검 순서 (사람 또는 승인된 연결 앱)
1. Gmail 수신함에서 내부 작업지시·GitHub 로봇 메일·광고·결제영수증을 **실제 고객**과 분리.
2. Netlify Forms 관리자에서 `order`, `feedback`, `consortium`, `contract-request`, `expert-apply`, `gcsme-member`, `partner-apply`, `unlock` 제출이 실제 기록되고 담당자에게 전달되는지 확인. 현 연결 환경에서는 자동 열람 불가.
3. 각 고객의 비공개 ID에 원문 채널·접수시각(시각대)·담당·다음 조치·정정/환불 증거 보존.
4. 보안·결제·개인정보 이슈는 일반 상담보다 먼저 담당자에게 보류/긴급 통지. API 키·접근코드 유출 신고가 있다면 실제 키 교체 경로를 안내하고 티켓에 비밀값 복제 금지.
5. 상담 결과 통보 전 대표/담당자가 실제 수행 가능성과 금액·계약 주체를 확인. 고객 개인 메일 자동 발신은 별도 승인 없이는 금지.
6. 사이트 운영 데이터(USGS/NWS/조달) 오류 신고는 국가·원문·수집 시각·게시 시각을 구분하며 수집이 성공하지 않은 데이터를 최신으로 표기하지 않는다.

## 5. 운영 공개 전 테스트 (필수)
- 익명 고객이 7개 언어 상담·견적·환불·도움말·접수 완료 페이지를 볼 수 있어야 함 (PR #361/#362).
- 서버 측 폼 개인정보 동의·봇 방지·허용된 응답 경로 및 GET 405 검증 필요 (PR #353); 브라우저 폼 존재만으로 충분하지 않음.
- 실제 고객 데이터 대신 승인된 테스트 계정으로 전송/도달/중복/후속메일 확인. 사용자 승인 없는 실 POST 금지.
- 모든 고객 가격은 M1 20,000/200,000 **VAT 포함** 일치, 카드 결제는 아직 검증 전.
- KO/EN/ES/FR/AR/VI/ID 공개 FAQ 검색은 네트워크 호출·로그인 요구 없이 작동, GCSME 법인 구분 명확.
- 공개 페이지에서 당일/1영업일/1~2영업일 약속이 다르게 쓰이는 부분은 담당자 승인 이후 하나의 계약상 응답 기준으로 정리. 합의 전 새 SLA 발명 금지.
- 실제 Cloudflare/Netlify 공개 배포, 도메인 매핑, 구독·과금 활성화는 별도 승인 후 수행.

## 6. 고객에게 안내할 원칙
- 재난 긴급 대응·개인 건강·투자·입찰 법률 판단은 자동 답변이 아닌 공식 기관 정보와 전문가 판단을 우선.
- 일반 질문은 7개 언어 검색 FAQ로 바로 확인 가능하되, **자동 접수/자동 해결을 보장하지 않는다**.
- 답변 근거가 없으면 '조사 중/미검증'으로 기록하고 근거가 나온 이후만 확정.
